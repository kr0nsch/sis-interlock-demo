# Правила разработки

## Контекст
- Репозиторий входит в открытое портфолио инженера АСУ ТП (kr0nsch, github.com/kr0nsch). Читают технические руководители интеграторов, машиностроителей и вендоров ПЛК. Качество и честность важнее объёма.
- Платформа по умолчанию: CODESYS V3.5 (3.5.17.30 — V3.5 SP17 Patch 3), целевой ПЛК — ОВЕН ПЛК210 (версию таргет-файла сверить с прошивкой). Без железа — CODESYS Control Win V3: без лицензии он работает 2 часа.
- Отечественные среды (Astra.IDE, MasterSCADA 4D, «Полигон») — только там, где этого требует задача.
- Путь к CODESYS — в переменной окружения `CODESYS_EXE`, профиль — в `CODESYS_PROFILE`. Если их нет, CODESYS недоступен: шаги в IDE описывай в `docs/MANUAL_STEPS.md`.

## Язык
- Идентификаторы — только ASCII, по-английски. Комментарии в коде и документация — по-русски.
- README — по-русски, плюс раздел `Summary (EN)` на 5–8 строк.
- Кодировка UTF-8 без BOM, переводы строк LF (кроме `.bat` и `.cmd`).

## Раскладка исходников ST
Источник истины — текстовые файлы, а не `.project`.

```
src/
  DUTs/<Name>.dut.st                 TYPE ... END_TYPE
  GVLs/<Name>.gvl.st                 VAR_GLOBAL ... END_VAR
  Interfaces/<I_Name>/
    <I_Name>.itf.st                  INTERFACE I_Name (EXTENDS ...)
    <Method>.method.decl.st          объявление метода
  POUs/<Name>/
    <Name>.decl.st                   PROGRAM / FUNCTION_BLOCK / FUNCTION и секции VAR
    <Name>.impl.st                   тело
    <Method>.method.decl.st
    <Method>.method.impl.st
    <Prop>.prop.decl.st
    <Prop>.get.impl.st
    <Prop>.set.impl.st
tests/                               тесты CfUnit в той же раскладке
```

- Один объект CODESYS — один файл или папка. Имя файла совпадает с именем объекта.
- `tools/assemble.py` склеивает POU в стандартный ST в `build/assembled/` — для iec_checker и RuSTy.
- `tools/codesys/import_sources.py` и `export_sources.py` (IronPython 2.7, CODESYS Scripting) импортируют исходники в проект и экспортируют обратно. После правок в IDE — экспорт в `src/` перед коммитом.
- `.project` в git не храним: он собирается из `src/`. Готовые `.project` и `.library` прикладываем к релизам GitHub.

## Именование ST
- POU: `PRG_`, `FB_`, `F_`. Типы: `ST_` — структура, `E_` — перечисление, `U_` — объединение. Интерфейсы — `I_`. Списки глобальных переменных — `GVL_`.
- Методы и свойства — PascalCase без префиксов: `Reset()`, `Value`.
- Переменные — с префиксом типа: x BOOL, b BYTE, w WORD, dw DWORD, i INT, di DINT, ui UINT, udi UDINT, r REAL, lr LREAL, s STRING, ws WSTRING, t TIME, e перечисление, st структура, a массив (можно с префиксом типа элемента: `astAlarm` — массив структур, `afbAlarm` — экземпляров ФБ, `axFlag` — BOOL), fb экземпляр ФБ, p указатель, ref ссылка, itf интерфейс.
- Физические величины — с единицами в имени: `rLevel_m`, `rPressure_bar`, `rFlow_m3h`.
- Константы — `VAR_GLOBAL CONSTANT` в `GVL_Const`, UPPER_SNAKE_CASE. «Магических чисел» в логике нет.
- В начале каждого POU — комментарий: назначение, автор, версия, ссылка на документ в `docs/`.

## Инженерные правила
- Время — через таймеры или источник времени, не через счёт циклов.
- У каждого устройства: режимы (авто, ручной, местный, вывод из работы), безопасное состояние при отказе, диагностика со статусами NAMUR NE 107, квитирование.
- Аналоговые входы 4–20 мА — с проверкой достоверности по NAMUR NE 43.
- Обмен с HMI и SCADA — через структуры команд и состояний (`ST_<Dev>Cmd`, `ST_<Dev>Sts`), а не россыпь переменных.
- Библиотеки — только стандартные CODESYS (Standard, Util, CAA) и открытые с совместимой лицензией. Проприетарные библиотеки вендоров — за адаптером и не в репозитории.
- ПАЗ и безопасность — только как демонстрация логики, с явным дисклеймером.

## Тесты и проверки
- ST: юнит-тесты на CfUnit (MIT, порт TcUnit). У каждого публичного ФБ и функции — тесты граничных условий и отказов.
- Python: pytest, ruff, mypy для новых модулей.
- Статанализ: `iec_checker` по `build/assembled/`. Находки исправить или обосновать в `docs/STATIC_ANALYSIS.md`.
- Если CODESYS доступен: импорт → сборка → для тестов запуск в CODESYS Control Win. Результаты — в `docs/TEST_REPORT.md`.

## Ограничения
- Никакого кода, названий объектов, схем и данных реальных заказчиков. Объекты — вымышленные, но правдоподобные.
- Не копируй код OSCAT, вендорских примеров и чужих репозиториев. Чужие идеи — со ссылкой. Документы вендоров (PDF с протоколами) не коммить, только ссылки.
- Не выдумывай требования стандартов и параметры приборов. Если не уверен — пометь «сверить с источником» и укажи, где проверить.
- Не утверждай непроверенное: «проверено в CODESYS» пишем только после реального прогона.

## Процесс
1. Перед реализацией — план: этапы, затрагиваемые файлы, риски, открытые вопросы.
2. Допущения и принятые решения — в `docs/ASSUMPTIONS.md`.
3. Небольшие коммиты в стиле Conventional Commits: `feat:`, `fix:`, `test:`, `docs:`, `chore:`.
4. После каждого этапа — проверки. Красные тесты в `main` не попадают.
5. В конце этапа: README, CHANGELOG, `docs/MANUAL_STEPS.md` с пошаговыми действиями в IDE и отчёт: сделано, проверено, осталось.

## README каждого проекта
Читатель — инженер АСУ ТП или техлид, который видит репозиторий впервые. Первый экран (баннер, строка
о проекте, бейджи, до ~6 строк текста) отвечает: что это, какую боль инженера снимает, для кого.
1. Баннер, строка о проекте, бейджи: CI, лицензия, версия CODESYS, выпуск.
2. «Что это и зачем» — 2–4 предложения, список «Что даёт», «Для кого».
3. «Как это выглядит» — GIF и снимки с подписью в одну строку: что видно на картинке.
4. «Быстрый старт» — шаги, которые работают на чистой машине без железа: версии, точные команды,
   «увидите: …» после каждой; отдельно — что требует CODESYS.
5. «Как использовать в своём проекте» — основной рабочий сценарий с проверенным примером.
6. «Как устроено» — диаграмма Mermaid и таблица «каталог → назначение».
7. «Тесты и качество» — что проверено и как; честно, что прогнано в CODESYS, а что не проверялось на железе.
8. «Документация» — таблица «документ → на какой вопрос отвечает».
9. «Ограничения и планы».
10. «Связанные проекты» — место в портфолио; ссылки только на опубликованные репозитории.
11. Summary (EN) на 5–8 строк.
12. Лицензия.

Каждая команда, путь, ключ и число в README проверяются прогоном; длинные справочные разделы — в `docs/`.
